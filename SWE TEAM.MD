# JARVIS — Autonomous Software Engineering System

## What This Is

An autonomous system that takes a product idea and ships it to production. You describe what you want. JARVIS handles specification, architecture, implementation, testing, security, and deployment without manual intervention.

The only costs are infrastructure hosting and LLM inference. Every tool in the stack is open source and self-hostable. No vendor lock-in, no per-seat SaaS fees.

## Design Principles

These aren't aspirational. They're constraints that every decision in this document must satisfy.

**1. Open source or don't use it.** Every tool that touches code, testing, security, orchestration, or observability must be open source and self-hostable. The only exceptions are hosting platforms (Vercel, Railway, Supabase) and LLM inference (OpenRouter). If a self-hosted alternative exists on the free tier, prefer it.

**2. Free models do the grunt work.** Most software engineering work is not reasoning-heavy. Generating a React component from a spec, writing a unit test, fixing a lint error, updating documentation — these tasks don't need frontier models. Use the cheapest model that produces correct output. Composer 2.5 has demonstrated strong code generation when given detailed enough plans. Use it for the bulk of implementation work and reserve expensive models for the decisions that are costly to reverse.

**3. Plans before code.** The single biggest waste of LLM tokens is generating code from vague instructions, watching it fail, and regenerating. The architecture explicitly separates planning (Product Agent, Architect Agent, Design Agent) from implementation (coding agents). Planning agents produce detailed, unambiguous specs. Coding agents consume specs and produce code. This separation pays for itself immediately in token savings and output quality.

**4. Agents don't trust themselves.** The agent that writes the code cannot approve it. The agent that designs the architecture doesn't implement it. QA doesn't read source — it exercises the running application. Security doesn't ask an LLM to "check for vulnerabilities" — it runs Semgrep, Trivy, and ZAP. Every stage has a separate agent with independent verification.

**5. Fail fast, fix autonomously, escalate honestly.** When QA fails, JARVIS routes the failure back to the responsible agent with the test output, the relevant code, and the original spec. The agent fixes it, Code Review reviews the fix, and it goes through the pipeline again. After 3 failed attempts on the same issue, JARVIS stops looping and tells you what's wrong, what it tried, and why it didn't work. No infinite loops, no silent failures.

**6. Forward-only data, immutable deployments.** Database migrations never delete or rename in place. Deployments are tagged, immutable, and rollback-able. Production state is always recoverable.

**7. No AI-slop UI. Ever.** Every product JARVIS ships must look like it was designed by someone with taste, not generated by a prompt. This means: use existing, high-quality open-source component libraries (ReactBits, shadcn/ui, Radix, Framer Motion) instead of building from raw Tailwind. Animations and micro-interactions are mandatory, not nice-to-haves. If the output looks like a generic "Build a SaaS in 10 minutes with AI" screenshot, it goes back to the Design Agent. This rule applies to every project JARVIS builds — not just the JARVIS dashboard itself.

## Agents

### JARVIS — Orchestrator

**Stack:** [LangGraph](https://github.com/langchain-ai/langgraph) (MIT) + PostgreSQL for state

JARVIS is the CTO. It doesn't write code. It maintains the task graph, assigns work, resolves dependencies, enforces budgets, and decides when things move forward.

**What it controls:**
- Task decomposition and dependency ordering
- Agent assignment (which agent gets which task)
- Token budget allocation and enforcement
- Retry logic with circuit breakers
- Deployment gate approvals
- Human escalation when automated repair fails

**Hard rules JARVIS enforces:**
- No engineering starts until the Architect Agent has produced API contracts and the Product Agent has produced acceptance criteria.
- No PR merges without Code Review Agent approval.
- No promotion to QC until DEV smoke tests pass.
- No production deployment while any HIGH or CRITICAL security finding is open.
- No infinite loops — 3 failures on the same task triggers human escalation.

**Model:** Tier 2 (Sonnet-class). JARVIS makes routing decisions, not implementation decisions. It doesn't need frontier reasoning.

### Product Agent

**Job:** Turn `"Build me a platform for athletes"` into structured, testable requirements.

**Outputs (committed to `docs/product/`):**
- Product requirements document with explicit scope boundaries
- User stories with acceptance criteria written as Given/When/Then
- MVP feature list ranked by priority
- Non-functional requirements (performance targets, scale expectations, compliance needs)
- Edge cases and known constraints

**Best practice:** Every user story must have at least one acceptance criterion that a QA agent can verify against the running application. Vague criteria like "should be fast" get rejected. Specific criteria like "dashboard loads in under 2 seconds on a 4G connection" are accepted.

**Model:** Tier 2 for initial drafting. Tier 1 (Opus-class) if requirements are ambiguous and need deep reasoning about tradeoffs.

---

### Architect Agent

**Job:** Define the technical shape of the system before anyone writes code.

**Outputs (committed to `docs/architecture/` and `docs/api/`):**
- System architecture with clear service boundaries
- API contracts as OpenAPI 3.1 YAML — these are the source of truth that Frontend and Backend agents both consume
- Database schema design (tables, relationships, indexes, RLS policies)
- Architecture Decision Records explaining *why* a technology or pattern was chosen, not just *what* was chosen
- Sequence diagrams for flows that cross service boundaries (auth, payment, real-time updates)

**Best practice:** ADRs follow the format: Context → Decision → Consequences. Every ADR must state what alternatives were considered and why they were rejected. This prevents the same debates from resurfacing when agents retry or when you review.

**Model:** Always Tier 1 (Opus-class). Architecture decisions are the most expensive to reverse. Getting them wrong wastes far more tokens than the cost of using a better model upfront.

---

### Design Agent

**Job:** Define UX structure, user flows, and design constraints that the Frontend Agent implements. The output must feel like a product designed by someone with taste, not a generic AI-generated dashboard with card grids and gradient buttons.

**Outputs (committed to `docs/design/`):**
- User flow descriptions (step-by-step, not just "user logs in")
- Component hierarchy and layout structure
- Design tokens (colors, spacing, typography, border radii) as a JSON file the frontend consumes
- Responsive breakpoints and mobile-first constraints
- Accessibility requirements — WCAG 2.1 AA minimum, with specific callouts (keyboard navigation, screen reader labels, color contrast ratios)
- **Component library selection** — which existing, polished UI library to use for this project (see approved list below)

**Anti-slop rule:** The Design Agent must never spec a UI from scratch when a high-quality open-source component library already solves the problem. AI-generated UI from raw Tailwind is identifiable from a mile away — the same card layouts, the same purple gradients, the same generic dashboard feel. Instead, the Design Agent selects from curated libraries that have real design craft behind them, and the Frontend Agent implements using those libraries.

**Approved UI libraries (use these, don't reinvent):**

| Library | What It's Good For | License |
|---|---|---|
| [ReactBits](https://reactbits.dev) | Animated, polished UI components with real visual personality — text effects, animations, backgrounds, interactive elements. Use when the product needs to feel alive, not clinical. | MIT |
| [shadcn/ui](https://ui.shadcn.com) | Copy-paste Radix-based primitives. Clean, unstyled foundation you customize. Best for dashboards and data-heavy interfaces where you want consistency without visual noise. | MIT |
| [Radix Primitives](https://www.radix-ui.com) | Headless, accessible primitives (dialogs, dropdowns, popovers, tabs). Use as the foundation under any custom styling. Handles keyboard nav, focus management, and ARIA for you. | MIT |
| [Framer Motion](https://www.framer.com/motion/) | Animation library. Page transitions, layout animations, gesture interactions. Use instead of writing CSS transitions by hand. | MIT |
| [cmdk](https://cmdk.paco.me) | Command palette (Cmd+K). If the product has any kind of search or command interface, use this. | MIT |
| [Sonner](https://sonner.emilkowal.ski) | Toast notifications done right. No building custom toast systems. | MIT |
| [Vaul](https://vaul.emilkowal.ski) | Mobile drawer component. Use for bottom sheets on mobile viewports. | MIT |
| [React Email](https://react.email) | Transactional emails. If the product sends emails, build them as React components. | MIT |

**How this works in practice:**

1. Design Agent specs a feature: "The athlete profile page needs a card with stats, an animated entrance, and a command palette for quick navigation."
2. Design Agent selects: ReactBits for the animated card + stat display, cmdk for the command palette, Framer Motion for page transitions, shadcn/ui for the data table showing training history.
3. Frontend Agent receives the spec with explicit library references and implements using those libraries — not from scratch.

This applies to **every project JARVIS builds**, not just the JARVIS dashboard itself. When JARVIS ships a product for athletes, for restaurants, for whatever — the Design Agent always starts from existing high-quality UI libraries and customizes, never from raw `div` + Tailwind.

**Best practice:** The Design Agent uses Playwright screenshots of the deployed QC environment to verify its specs against the actual rendered UI. This catches "the design says X but the implementation shows Y" drift without a human eyeballing it.

**Model:** Tier 2 default. Tier 3 (Composer 2.5) for straightforward design token updates.

### Frontend Agent

**Stack:** Next.js, React, TypeScript. Deployed to Vercel.
**Scope:** `frontend/`

**Responsibilities:**
- Pages, components, forms, and layouts — implementing Design Agent specs **using the specified UI libraries**
- API integration — consuming the OpenAPI contracts from Architect Agent
- Responsive implementation and accessibility
- Unit tests (Vitest) and component tests (Testing Library)
- Performance: code splitting, lazy loading, image optimization via `next/image`

**Best practices the agent must follow:**
- No `any` types. TypeScript strict mode enforced.
- API response types auto-generated from OpenAPI contracts using `openapi-typescript`. No manual type definitions for API data.
- Components follow the container/presenter pattern. Business logic stays in hooks, not in JSX.
- Every interactive element has keyboard support and an accessible label.
- Bundle size checked in CI. New dependencies over 50KB require justification.
- **Use the UI libraries the Design Agent specified.** If the spec says "use ReactBits animated card," use ReactBits. Don't recreate the component from scratch in Tailwind. The whole point is leveraging work done by designers who actually care about details like easing curves, shadow depth, and hover states.
- **No generic AI patterns.** These are explicitly banned:
  - Card grids with identical padding and a subtle box-shadow as the default layout for everything
  - Purple/blue gradients on CTAs for no design reason
  - Hero sections with centered text + a single "Get Started" button over a stock illustration
  - Dashboards where every metric is a rounded card with an icon and a number
  - Generic "modern SaaS" layouts that look like every AI-generated landing page

  If the agent produces something that looks like it could be a screenshot in a "Build a SaaS with AI" tutorial, it has failed. The Design Agent's spec includes specific library choices and visual references precisely to prevent this.
- **Animations and interactions are not optional.** If the Design Agent spec includes Framer Motion page transitions or ReactBits animated elements, implement them. Don't skip animations to save time. Static UIs feel lifeless and cheap — the difference between a product that feels crafted and one that feels generated is in the micro-interactions.

**Model:** Composer 2.5 for implementation when the plan is detailed (which it always should be, because the Architect and Design agents produce the spec first). Escalate to Tier 2 (Sonnet-class) for complex state management, performance optimization, or debugging cross-browser issues.

### Backend Agent

**Stack:** Python/FastAPI or TypeScript/Express. Deployed to Railway.
**Scope:** `backend/`

**Responsibilities:**
- REST API implementation matching Architect Agent's OpenAPI contracts
- Authentication and authorization (Supabase Auth + RLS as primary, API-level checks as backup)
- Business logic, input validation (Pydantic or Zod), and error handling
- Background jobs and scheduled tasks
- Third-party integrations
- Unit tests and integration tests

**Best practices the agent must follow:**
- Every endpoint validates input with a schema. No trusting raw request bodies.
- Errors return structured JSON with a machine-readable error code, a human-readable message, and a correlation ID for debugging.
- Secrets come from environment variables, never hardcoded. The agent doesn't commit `.env` files.
- Database queries use parameterized statements. No string interpolation in SQL.
- Rate limiting on all public endpoints. Token bucket algorithm, configured per-route.
- Structured logging with correlation IDs that trace a request from ingress to response.

**Model:** Composer 2.5 for standard CRUD implementation with clear specs. Tier 2 (Sonnet-class) for auth flows, complex business logic, or security-sensitive code. Tier 1 (Opus-class) for debugging production issues or designing retry/idempotency logic.

### AI/ML Agent

**Gateway:** [OpenRouter](https://openrouter.ai/)
**Scope:** `ai/`

**Responsibilities:**
- LLM integration for product features (not for JARVIS itself — that's the orchestration layer)
- RAG pipelines: chunking strategy, embedding model selection, retrieval tuning
- Prompt engineering with version-controlled prompts (prompts are code, not magic strings)
- Structured output schemas and output validation
- Model fallback chains (if primary model is down or too slow, fall back gracefully)
- Cost estimation per feature (tokens per request * expected request volume = projected cost)

**Best practice:** Every prompt is stored as a versioned template file, not inline in code. This makes prompts reviewable, testable, and diffable. The AI/ML Agent writes evals (input/expected-output pairs) for every prompt, so prompt changes can be regression-tested.

**Model:** Tier 2 default. This is the one area where expensive models are justified for the *product's* features (not for JARVIS's internal work).

### Database Agent

**Stack:** PostgreSQL via [Supabase](https://supabase.com/)
**Scope:** `database/`, `supabase/`, `migrations/`

**Responsibilities:**
- Schema design and migration files
- Index strategy (explain the query plan, don't just add indexes blindly)
- Row Level Security policies — every table must have RLS enabled with explicit policies
- Seed data for DEV and QC environments
- Data integrity constraints (foreign keys, check constraints, unique constraints, not-null)

**Hard rules:**
- The Database Agent never runs anything directly against production. It writes a migration file. That migration goes through `DEV → QC → QA gate → RELEASE → PROD`.
- Migrations are forward-only. See [Database Discipline](#database-discipline).
- Every migration file has a corresponding rollback migration (which is itself a forward migration that reverses the change).

**Best practice:** After writing a migration, the Database Agent writes a test that verifies the migration applies cleanly, the rollback migration applies cleanly, and the schema matches the expected state. This runs in CI against a throwaway database.

**Model:** Composer 2.5 for straightforward schema additions. Tier 2 (Sonnet-class) for index optimization, RLS policy design, or complex migration sequences.

### Code Review Agent

**Position:** Gates every PR before merge to `develop`. The authoring agent cannot approve its own work.

**What it checks:**
- Does the code implement what the spec asked for? (Compare PR against the task spec from Product/Architect Agent)
- Does it follow the project's established patterns? (Compare against existing code via RAG)
- Are there obvious bugs, off-by-one errors, or unhandled edge cases?
- Does it have tests? New functionality without tests gets rejected.
- Are there security anti-patterns? (SQL injection, XSS vectors, hardcoded secrets, overly permissive CORS)
- Is error handling complete? (No bare `catch {}` blocks, no swallowed errors)

**What it does NOT check:** Style, formatting, import order. Those are handled by automated linters in CI (ESLint, Prettier, Ruff). The Code Review Agent focuses on logic, not aesthetics.

**Output:** Structured review with a verdict (approve / request changes / block) and line-level comments. If it requests changes, it explains *what* is wrong and *why*, not just "fix this."

**Model:** Tier 2 (Sonnet-class) default. Tier 1 (Opus-class) for PRs touching auth, payments, or data deletion.

### QA Agent

**Stack:** [Playwright](https://github.com/microsoft/playwright) (Apache 2.0)
**Target:** QC environment (not source code)

This agent doesn't read code. It opens a browser, uses the application like a human would, and reports what breaks.

**Test strategy (testing pyramid, not inverted):**

```
         ┌──────┐
         │ E2E  │  ← QA Agent: critical user journeys only
         ├──────┤
       ┌─┤ Intg │  ← Coding agents: API contract tests, DB integration
       │ ├──────┤
       │ │ Unit │  ← Coding agents: business logic, pure functions
       └─┴──────┘
```

The QA Agent owns the top of the pyramid — end-to-end tests that exercise the full stack through the browser. It does not duplicate the unit and integration tests that coding agents already write.

**What it tests:**
- Critical user journeys (signup → onboard → core action → result)
- Form validation (required fields, invalid input, edge cases)
- Authentication flows (login, logout, session expiry, password reset)
- Authorization (can user A see user B's data? They shouldn't.)
- Cross-browser rendering (Chromium, Firefox, WebKit)
- Mobile viewport (375px width minimum)
- Error states (what happens when the API is down? when the user submits bad data?)
- Data persistence (create something, refresh the page, is it still there?)

**Best practice:** Tests are deterministic. No flaky tests. If a test depends on timing, it uses Playwright's built-in `waitFor` patterns, not `sleep`. If a test depends on data, it creates its own test data and cleans up after itself.

**Model:** Tier 3 (Composer 2.5) for generating test scripts from spec descriptions. QA work is template-heavy and spec-driven — exactly the kind of work where a fast, cheap model with a good plan outperforms an expensive model with a vague prompt.

### Security Agent

This agent runs tools, not vibes. It doesn't ask an LLM to "review for security." It runs three open-source scanners and interprets their output.

**Tool chain:**

| Tool | What It Does | License |
|---|---|---|
| [Semgrep CE](https://github.com/semgrep/semgrep) | Static analysis — finds code patterns that match known vulnerability classes (SQL injection, XSS, insecure crypto, hardcoded secrets) | LGPL 2.1 |
| [Trivy](https://github.com/aquasecurity/trivy) | Dependency scanning (known CVEs in npm/pip packages), container image scanning, IaC misconfiguration detection | Apache 2.0 |
| [OWASP ZAP](https://github.com/zaproxy/zaproxy) | Dynamic testing — crawls the running QC application and probes for vulnerabilities (injection, broken auth, misconfigured headers) | Apache 2.0 |

All three run in parallel. The Security Agent collects their reports, deduplicates findings, assigns severity (CRITICAL / HIGH / MEDIUM / LOW / INFO), and passes the consolidated report to JARVIS.

**Blocking rules:**
- CRITICAL or HIGH → pipeline blocked until fixed
- MEDIUM → flagged for review, does not block
- LOW / INFO → logged for awareness, no action required

**Model:** Tier 3 (Composer 2.5). The LLM's job here is to parse tool output and generate a structured report. The tools do the actual security analysis.

### DevOps Agent

**Scope:** `infra/`, `.github/workflows/`, `Dockerfile`, `docker-compose.yml`

**Responsibilities:**
- Dockerfiles and container configuration (multi-stage builds, minimal base images, non-root users)
- GitHub Actions workflow definitions
- Environment variable management (never committed, documented in `docs/environments.md`)
- Deployment configuration for Vercel and Railway
- Health check endpoint implementation (`/healthz` returns 200 with dependency status)
- Migration execution scripts per environment

**Best practices:**
- Docker images use specific version tags, not `latest`.
- CI pipelines are deterministic — same commit always produces the same build artifact.
- Secrets are stored in GitHub Actions secrets / Vercel/Railway environment configs, never in the repo.
- Every deployment is tagged with the Git SHA. You can always trace a running deployment back to the exact commit.

**Model:** Composer 2.5 for Dockerfile and workflow YAML generation. Tier 2 (Sonnet-class) for debugging CI failures or designing new pipeline stages.

### Documentation Agent

**Scope:** `docs/`, `README.md`, `CHANGELOG.md`

Runs automatically after every successful production deployment.

**Outputs:**
- Changelog entry derived from the merged PRs since the last release
- Updated API documentation (auto-generated from the latest OpenAPI spec)
- Updated README if the project's setup instructions changed
- Runbook entries for new operational procedures

**Model:** Composer 2.5. Documentation generation from structured inputs (PR descriptions, OpenAPI specs, ADRs) is entirely template-driven work. No need for expensive models.

## How Agents Communicate

Three layers, each serving a different purpose.

### Layer 1 — Task State (LangGraph graph state)

JARVIS maintains a directed acyclic graph of tasks. Each task node:

```json
{
  "task_id": "uuid",
  "agent": "frontend",
  "status": "pending | in_progress | completed | failed | blocked",
  "depends_on": ["task-uuid-1", "task-uuid-2"],
  "input_artifacts": ["docs/api/contracts.yaml"],
  "output_artifacts": [],
  "model_tier": 3,
  "token_budget": 8000,
  "tokens_used": 0,
  "retry_count": 0,
  "max_retries": 3
}
```

JARVIS uses this to schedule work, resolve dependencies, and track spend.

### Layer 2 — Artifacts (Git repository)

Agents don't message each other. They produce artifacts — files committed to the repo that downstream agents consume.

```
repo/
├── docs/
│   ├── product/           ← Product Agent: PRDs, user stories
│   ├── architecture/      ← Architect Agent: system design, ADRs
│   ├── api/               ← Architect Agent: OpenAPI contracts
│   ├── design/            ← Design Agent: UX specs, design tokens
│   └── runbook/           ← Documentation Agent: operational procedures
├── frontend/              ← Frontend Agent
├── backend/               ← Backend Agent
├── ai/                    ← AI/ML Agent
├── database/
│   ├── migrations/        ← Database Agent
│   ├── seeds/             ← Database Agent
│   └── schema.sql         ← Database Agent: current schema snapshot
├── infra/
│   ├── docker/            ← DevOps Agent
│   └── monitoring/        ← DevOps Agent
├── tests/
│   └── e2e/               ← QA Agent: Playwright tests
├── .github/
│   └── workflows/         ← DevOps Agent: CI/CD pipelines
├── README.md
└── CHANGELOG.md
```

The API contract YAML is the critical handshake. Frontend Agent and Backend Agent both consume it. Neither invents their own API shape.

### Layer 3 — Structured Results (agent → JARVIS)

When an agent finishes (or gets stuck), it returns a structured result:

```json
{
  "agent": "backend",
  "task_id": "uuid",
  "status": "completed",
  "summary": "Implemented POST /api/v1/athletes with validation and tests",
  "artifacts_created": ["backend/src/routes/athletes.py", "backend/tests/test_athletes.py"],
  "artifacts_modified": ["backend/src/main.py"],
  "tokens_used": 4200,
  "blocking_issues": [],
  "needs_from": []
}
```

If blocked:

```json
{
  "agent": "frontend",
  "status": "blocked",
  "needs_from": [{
    "agent": "architect",
    "artifact": "docs/api/contracts.yaml",
    "reason": "API contract for /api/v1/athletes not yet defined"
  }]
}
```

JARVIS reads this, schedules the dependency, and re-queues the blocked task.

## Codebase Intelligence

LLMs have context limits. A 200-file project won't fit in a single prompt. Agents need a way to find and retrieve relevant code.

### Retrieval (RAG over the codebase)

```
Source files → chunk by function/class → embed (free embedding model) → store in pgvector (Supabase)
```

When an agent starts a task, it queries the vector store for relevant code. This replaces "paste the entire codebase into the prompt."

**Embedding model:** Use a free or near-free embedding model via OpenRouter (e.g., `text-embedding-3-small` at $0.02/1M tokens — effectively free at project scale). Alternatives: self-hosted [Sentence Transformers](https://github.com/UKPLab/sentence-transformers) (Apache 2.0) for zero-cost embeddings.

**Indexing triggers:**
- Full index on project initialization
- Incremental re-index on every merge to `develop` (only changed files)

### Context Package

Before any task, JARVIS assembles a context package for the agent:

1. **Role definition** — who you are, what you can and can't do
2. **Project summary** — auto-generated from README, architecture docs
3. **Task spec** — the specific thing to build/fix, with acceptance criteria
4. **Relevant code** — retrieved via RAG based on the task description
5. **Relevant artifacts** — API contracts, design specs, schema definitions
6. **Previous attempts** — if this is a retry, include the failure output and the code that caused it

This means agents don't start cold. They start with focused, relevant context instead of either nothing or everything.

### Shared Knowledge

Some information is globally relevant. These files are always included in every agent's context (they're small enough to include directly):

- `docs/api/contracts.yaml` — the current API contract
- `database/schema.sql` — the current database schema
- `docs/architecture/decisions.md` — active ADRs
- `docs/design/tokens.json` — design system tokens

## Deployment Pipeline

### The Environments

| Environment | Purpose | Mirrors Production? |
|---|---|---|
| DEV | Integration testing. Does the new code work when merged? | Partially |
| QC | Pre-production validation. Where QA and Security agents test. | Yes — same architecture, config, deployment mechanism |
| Production | Live. Real users, real data. | — |

QA is a process, not an environment. The QA Agent tests against QC.

### Stage 0 — Agent Workspace

```
JARVIS assigns task
  → OpenHands worker spins up in Docker
  → Agent creates branch: feature/TASK-123-short-description
  → Agent writes code + tests
  → Agent runs: lint, type check, unit tests
  → All pass → agent opens PR against develop
  → Code Review Agent reviews
  → Approved → merge
```

**Gate:** Nothing merges without passing lint + types + unit tests + Code Review approval.

### Stage 1 — DEV

On merge to `develop`, GitHub Actions triggers:

```
Lint + type check
Unit tests
Integration tests
Build (frontend + backend)
Semgrep (SAST)
Trivy (dependency scan)
Secret detection (trufflehog or gitleaks, both open source)
Deploy to DEV (Vercel preview + Railway dev + Supabase dev)
Smoke tests against DEV
```

**Gate:** All checks green before promoting to QC.

**Best practice:** CI jobs run in parallel where possible. Lint, types, and unit tests are independent — run them concurrently. Semgrep, Trivy, and secret scanning are independent — run them concurrently. Build depends on lint+types passing. Deploy depends on build passing. Smoke tests depend on deploy.

### Stage 2 — QC

Promotion to QC creates a release candidate branch and deploys to the QC environment:

```
Vercel QC    (frontend, production-equivalent config)
Railway QC   (backend, production-equivalent config)
Supabase QC  (database, production-equivalent schema, separate data)
```

QC uses the same deployment mechanism as production. If it deploys to QC, it will deploy to production the same way.

### Stage 3 — QA Gate

QA Agent and Security Agent attack QC in parallel:

```
QC ready
  │
  ├── QA Agent: Playwright E2E tests (Chromium + Firefox + WebKit + mobile)
  ├── QA Agent: API contract tests (every endpoint, valid + invalid inputs)
  ├── Security Agent: Semgrep scan
  ├── Security Agent: Trivy scan
  └── Security Agent: ZAP dynamic scan against running QC app
  │
  ▼
Combined report → JARVIS
```

**If any test fails:**
JARVIS identifies the responsible agent from the failure context, sends the agent the failing test output + relevant code + original spec, and the agent produces a fix. The fix goes through Code Review → merge → DEV → QC → QA again. Max 3 retries per issue.

**If all tests pass:**
The release candidate moves to the Release Gate.

### Stage 4 — Release Gate

Before production:
- All QA tests green
- Zero CRITICAL/HIGH security findings
- Migration dry-run succeeds against production schema (checks for conflicts without applying)
- Deployment config validated
- JARVIS produces a release summary (what changed, what was tested, risk assessment)

**V1:** You approve production releases manually after reviewing JARVIS's summary.
**V2+:** Low-risk releases (no schema changes, no auth changes, only additive features) auto-deploy. High-risk releases still require human approval.

### Stage 5 — Production

```
Release tag created (vX.Y.Z)
  → Deploy frontend to Vercel production
  → Deploy backend to Railway production
  → Run database migration against Supabase production
  → Health check verification (every 10s for 5 minutes)
  → Post-deploy smoke tests
  → Documentation Agent generates changelog
  → Deployment recorded (SHA, timestamp, what changed)
```

## Parallel Execution

LangGraph supports parallel branches natively. Use them.

**Planning phase:** Product Agent runs first (needs your input). Then Architect and Design agents run in parallel — they have different outputs with no dependency on each other.

**Engineering phase:** Once API contracts and database schema exist, Frontend, Backend, and AI/ML agents all work in parallel. The API contract is their shared interface. They don't need to wait for each other.

**QA phase:** Playwright tests, API tests, and all three security scans (Semgrep, Trivy, ZAP) run concurrently. Zero dependencies between them.

**Estimated time savings:** 40-60% compared to running everything sequentially. On a feature that takes 30 minutes of LLM time sequentially, parallelism brings it to 12-18 minutes.

## Model Routing and Cost Control

### The Philosophy

Most agent work is mechanical: take a detailed spec, produce code that matches. This is exactly where fast, cheap models excel. The expensive work is upstream — deciding *what* to build and *how* to structure it. Spend tokens on planning, save tokens on implementation.

### Model Tiers

| Tier | Role | Models | When to Use |
|---|---|---|---|
| **Tier 0 — Free** | Coding grunt work | Composer 2.5, Gemma 3, Llama 4 Scout (via OpenRouter free tier or self-hosted) | Implementation from detailed specs. Boilerplate. Test generation. Documentation. Linting fixes. Dockerfile/YAML generation. Any task where the plan is already complete and unambiguous. |
| **Tier 1 — Cheap** | Standard coding | Claude Haiku, GPT-4o-mini | Moderate complexity tasks. Writing integration tests. Parsing and summarizing tool output (security reports, QA results). |
| **Tier 2 — Mid** | Reasoning-heavy | Claude Sonnet, GPT-4o | Complex business logic. Auth flows. State management. Code review. Debugging. Tasks where the agent needs to make judgment calls. |
| **Tier 3 — Premium** | High-stakes decisions | Claude Opus, o3 | Architecture design. Migration strategy for production databases. Security-critical code. Decisions that are expensive to reverse. |

### Default Model Per Agent

| Agent | Default Tier | Escalation Trigger |
|---|---|---|
| JARVIS (orchestrator) | Tier 2 | — |
| Product Agent | Tier 2 | Ambiguous requirements → Tier 3 |
| Architect Agent | Tier 3 | Always. Architecture mistakes are the costliest. |
| Design Agent | Tier 1 | — |
| Frontend Agent | Tier 0 (Composer 2.5) | Complex state/perf issues → Tier 2 |
| Backend Agent | Tier 0 (Composer 2.5) | Auth/security code → Tier 2, production debugging → Tier 3 |
| AI/ML Agent | Tier 2 | — |
| Database Agent | Tier 0 (Composer 2.5) | Migration design → Tier 2, production migration → Tier 3 |
| Code Review Agent | Tier 2 | Security-sensitive PRs → Tier 3 |
| QA Agent | Tier 0 (Composer 2.5) | Writing new test strategy → Tier 2 |
| Security Agent | Tier 0 (Composer 2.5) | Just parsing tool output |
| DevOps Agent | Tier 0 (Composer 2.5) | New infra design → Tier 2 |
| Documentation Agent | Tier 0 (Composer 2.5) | Always. Pure template work. |

### Why Composer 2.5 for Most Implementation

Composer 2.5 has demonstrated strong code generation when given sufficiently detailed plans. The JARVIS architecture is specifically designed to produce those detailed plans:

1. Product Agent produces acceptance criteria with Given/When/Then format
2. Architect Agent produces OpenAPI contracts with request/response schemas
3. Design Agent produces component specs with props, state, and layout details

By the time a coding agent receives a task, the plan is detailed enough that Composer 2.5 can execute it reliably. The planning agents (which use Tier 2-3 models) have already done the hard thinking.

This is the key insight: **spend money on planning, save money on execution.**

### Cost Controls

**Token budgets:** Every task gets a token budget based on estimated complexity. If an agent exhausts its budget, JARVIS must explicitly approve additional tokens or reassign to a different agent/model.

**Prompt caching:** Agent role definitions (system prompts) are identical across invocations. OpenRouter's prompt caching reduces repeat costs significantly.

**Response caching:** Static context queries (project structure, current schema, active ADRs) are cached locally. If the underlying files haven't changed since the last query, return the cached result. No LLM call needed.

**Deduplication:** If two agents request the same context (e.g., both Frontend and Backend ask for the API contract), the embedding lookup happens once and the result is shared.

**Daily spend tracking:** JARVIS logs every LLM call with model, tokens, and cost. If 80% of the monthly budget is consumed before the 20th, non-critical tasks pause and you're notified.

**Self-hosted fallback:** For Tier 0 work, if OpenRouter free-tier models have rate limits or availability issues, fall back to self-hosted models via [Ollama](https://github.com/ollama/ollama) (MIT) or [vLLM](https://github.com/vllm-project/vllm) (Apache 2.0) running locally. This costs only electricity.

## Hardening the Product

Things the agents must build into every application JARVIS ships.

### Rate Limiting

Every public API endpoint gets rate limiting. Token bucket algorithm. Configurable per route. Default: 100 requests/minute per user. Auth endpoints: 10 requests/minute per IP (brute-force protection).

Implementation: middleware in FastAPI (`slowapi`, open source) or Express (`express-rate-limit`, MIT).

### Input Validation

Every endpoint validates input against a schema before processing. Use Pydantic (Python) or Zod (TypeScript). Invalid input returns 400 with a structured error explaining what's wrong. Never trust client-side validation alone.

### Error Handling

Errors return structured JSON:

```json
{
  "error": {
    "code": "ATHLETE_NOT_FOUND",
    "message": "No athlete found with ID 123",
    "correlation_id": "req-abc-456"
  }
}
```

The `correlation_id` traces through logs so you can follow a request's journey through the system. No bare exception swallowing. No generic "Internal Server Error" without a logged trace.

### Authentication and Authorization

Supabase Auth handles user identity. RLS policies on every table handle data access. Backend API endpoints verify the JWT and check permissions as a second layer. Defense in depth — if RLS has a gap, the API layer catches it, and vice versa.

### Health Checks

Every service exposes `/healthz` that returns:

```json
{
  "status": "healthy",
  "version": "1.2.3",
  "commit": "abc123",
  "dependencies": {
    "database": "connected",
    "supabase_auth": "connected"
  }
}
```

If any dependency is unreachable, status is `"degraded"` and the response code is 503.

### Feature Flags (V2+)

[Unleash](https://github.com/Unleash/unleash) (Apache 2.0, self-hosted). Enables:
- Ship code to production without activating it
- Canary releases (5% → 25% → 100%)
- Instant deactivation without redeployment

For V1, use environment-variable-based flags. Simple, no extra infrastructure.

### Performance

Frontend: Lighthouse CI in the pipeline. Target scores: Performance > 90, Accessibility > 95, Best Practices > 95.

Backend: Response time budget. p95 under 500ms for reads, under 1s for writes. Measured in QC environment during QA testing.

Database: Every query in the application has its `EXPLAIN ANALYZE` output reviewed by the Database Agent. No full table scans on tables expected to exceed 10K rows.

## Failure Recovery

### JARVIS State

JARVIS's task graph is persisted in PostgreSQL via LangGraph's built-in checkpointer. Every state transition is checkpointed:

```
Task created      → save
Agent assigned    → save
Agent completed   → save
Agent failed      → save
Pipeline advanced → save
```

If JARVIS crashes, it restarts from the last checkpoint. It checks Git for any work that completed while it was down (commits, PRs) and reconciles state.

### Dead Letter Queue

Tasks that fail `max_retries` times go to a dead letter table:

```sql
CREATE TABLE dead_letter_tasks (
  task_id       UUID PRIMARY KEY,
  agent         TEXT NOT NULL,
  error_summary TEXT NOT NULL,
  full_context  JSONB NOT NULL,
  attempts      INT NOT NULL,
  created_at    TIMESTAMPTZ DEFAULT now(),
  resolved      BOOLEAN DEFAULT FALSE,
  resolution    TEXT
);
```

JARVIS surfaces these to you with full context: what was attempted, what failed, the error output, and the code that was generated. You provide direction, JARVIS retries with your input.

### Circuit Breakers

- **Task-level:** 3 failures → dead letter
- **Agent-level:** If a single agent fails 5 tasks in a row, JARVIS pauses that agent and alerts you. Possible causes: broken system prompt, bad model, infra issue.
- **Budget-level:** If daily spend exceeds the daily budget (monthly/30), non-critical tasks pause. Critical tasks (production fixes) continue.

## Database Discipline

### Migrations Are Forward-Only

Never write a migration that destroys data. The rationale: if you need to rollback the application code, forward-only migrations mean the old code still works with the new schema.

| Don't | Do |
|---|---|
| `DROP COLUMN email` | `ALTER TABLE ADD COLUMN email_v2; UPDATE SET email_v2 = email;` then drop the old column in a future release after verifying nothing reads it |
| `ALTER TABLE RENAME users TO members` | `CREATE TABLE members AS SELECT * FROM users;` add the new table, migrate reads, then drop the old table later |
| `ALTER COLUMN age TYPE TEXT` | Add a new column `age_text`, backfill, migrate reads, drop old column later |

### Conflict Prevention

When multiple agents modify the schema on parallel branches:

1. **Migration lock:** JARVIS checks if any open QC candidate includes migration files. If yes, new schema changes wait until the current one clears QA.
2. **Timestamp-based naming:** `20260816143000_add_athletes_table.sql`. Ordered by creation time.
3. **CI validation:** Every PR with migration files runs `supabase db push --dry-run` against a fresh database to verify the migration applies cleanly.
4. **Schema snapshot:** After every production migration, `database/schema.sql` is regenerated. Agents use this as the current truth, not their memory of what the schema "should" look like.
5. **Cross-agent review:** Any PR touching `migrations/` gets reviewed by the Database Agent, regardless of who authored it.

## Rollback Procedures

### Frontend (Vercel)

Vercel keeps every deployment immutable. Rollback = promote the previous deployment.

- Trigger: health check failure or error spike post-deploy
- Method: `vercel rollback` CLI or dashboard
- Time: under 30 seconds

### Backend (Railway)

Railway retains previous builds. Rollback = redeploy the previous build.

- Trigger: health check failure, error spike, or smoke test failure
- Method: Railway CLI or dashboard
- Time: under 2 minutes

### Database

You don't rollback a database. You apply a new forward migration that reverses the change. See [Database Discipline](#database-discipline).

If a migration causes a production issue:
1. The Database Agent writes a new migration that reverses the problematic change (additive, not destructive).
2. That migration goes through the same pipeline: PR → review → DEV → QC → QA → production.
3. For urgent fixes, JARVIS can fast-track this pipeline (skip QC/QA for schema-only changes that add columns or create tables — these are inherently safe).

### Automated Rollback (V2+)

Post-deployment health checks run every 10 seconds for 5 minutes. If health checks fail 3 consecutive times:
1. Auto-rollback frontend (Vercel) and backend (Railway)
2. Do NOT auto-rollback database (forward-only)
3. Notify JARVIS → investigate → fix → redeploy through normal pipeline

## The Lifecycle

```
You: "Build X"
  │
  ▼
JARVIS receives intent
  → Product Agent: PRD + acceptance criteria (Tier 2)
  │
  ├── Architect Agent: API contracts + schema + ADRs (Tier 3)     ← parallel
  └── Design Agent: UX flows + design tokens (Tier 1)             ← parallel
  │
  ▼
JARVIS decomposes into task graph
  │
  ├── Frontend Agent: implement UI from specs (Composer 2.5)      ← parallel
  ├── Backend Agent: implement API from contracts (Composer 2.5)  ← parallel
  ├── AI/ML Agent: implement AI features (Tier 2)                 ← parallel
  └── Database Agent: write migrations (Composer 2.5)
  │
  ▼
Code Review Agent: review every PR (Tier 2)
  │
  ▼
Merge to develop → DEV environment
  → CI: lint, types, tests, build, SAST, SCA, secrets
  │
  ▼
Promote to QC
  │
  ├── QA Agent: Playwright tests (Composer 2.5)                   ← parallel
  └── Security Agent: Semgrep + Trivy + ZAP (Composer 2.5)       ← parallel
  │
  ├── FAIL → JARVIS → responsible agent → fix → Code Review → DEV → QC → QA again (max 3x)
  │
  ▼ PASS
Release Gate
  → Final checks + JARVIS risk summary
  → You approve (V1)
  │

Production
  → Vercel + Railway + Supabase

The point is not that you have a lot of agents.
